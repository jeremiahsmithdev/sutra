## Sources to read before writing the verdict

Use the Read and Bash tools to inspect these directly. Do NOT skip this step —
the verdict is worthless without it.

1. **The playlist file** — `Read {{PLAYLIST_PATH}}`. See what was supposed to happen.
2. **Parent epic descriptions** — for each ID in `{{EPIC_IDS}}`, run `br show <id>`.
   Read the epic's title, description, and any linked spec file the description
   points to (e.g. `docs/technical/features/<feature>_SPEC.md`). The verdict
   compares implementation against this stated intent.
3. **The diff this run produced** —
   `git diff {{SESSION_START_SHA}}..HEAD --stat` for the file-level overview, then
   `git diff {{SESSION_START_SHA}}..HEAD -- <path>` to drill into specific files.
   Open the 2–3 largest changed files with Read and assess them against the
   project's coding standards (CLAUDE.md if present at the repo root).
4. **Specific commits** — `git show <sha>` for any commit whose message
   suggests it might be problematic or interesting.

## Verdict rubric

Pick exactly one label for the Executive Summary. The label is the headline:

- **READY TO MERGE** — every playlist item closed, code matches epic intent,
  no obvious quality issues, tests likely passing. No follow-ups required.
- **READY WITH CAVEATS** — substantially complete and mergeable but has minor
  issues: untracked files, missing docs, small TODOs, low-impact follow-ups.
  List the caveats.
- **NEEDS WORK** — significant gaps: open beads, failed gates, unaddressed
  issues from review prompts, missing tests on important code paths,
  divergence from epic intent. Do not merge yet.
- **INCOMPLETE** — playlist did not finish, circuit breaker tripped, or large
  portions of the work are missing or stubbed. Resume next session.

If you find ANY issue worth a follow-up bead, list it explicitly. Be direct:
"create a P2 bug bead for the duplicated rate-limit logic in
application/services/integrations/xero/" beats "consider deduplicating".

## Rules

1. The Executive Summary verdict and Implementation Review are MANDATORY.
   Do not skip them. Do not write a stub. If you cannot form a verdict
   because tools failed, say so explicitly and choose INCOMPLETE.
2. Use Read and Bash to inspect sources first, write the report second.
   The verdict must be grounded in something you actually looked at.
3. Be opinionated. Ralph already shows you the run timeline; what's
   missing from prior reports is judgment. That's your contribution.
4. Do NOT commit the report. Leave it on disk at `{{REPORT_FILE}}` as a session
   artifact — the user decides whether to archive it.
5. Do NOT modify any files other than the report. Do NOT run br write commands
   (no `br update`, `br create`, `br close` — read-only `br show` only).
6. When done, just exit.
