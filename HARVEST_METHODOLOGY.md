# The Methodology Harvest

What you do after the work has been harvested — review the loop that produced it.

See also: [[Harvest.md]] | [[PHILOSOPHY.md]] | [[metrics.md]]

---

## The Cycle

[[Harvest.md]] processes the **work** a ralph run produced — the code, the beads, the tests. This document processes the **run itself** — the orchestration, the instructions, the gaps between planned and actual. The two harvests are peers. Do the work harvest first; a bad merge can't be undone by an insight about why it happened.

The methodology harvest asks one question: *given the same philosophy, can the next run be simpler, better aligned, or less redundant?* It is the mechanism by which the system around the model improves. The model improves on its own schedule. Everything else improves here.

## What the Methodology Harvest Produces

**A dated epic of improvement beads.** Findings become beads in ralph's own `.beads/`, labelled `self-improvement`, titled with an `HV:` prefix, parented to a single `Harvest YYYY-MM-DD HH:MM — <identifier>` epic. The epic is always created, even for single-finding runs, so the report always has one thing to point at.

**One concise report.** Written to `.ralph/harvests/<timestamp>.md`. Leads with the epic ID. Summarises findings ordered by guardrail severity. One file per run. The directory is the archive.

**Discarded candidates.** Most findings are rejected. The guardrails are not suggestions — they are filters. A finding that would move intelligence into the outer loop does not become a bead regardless of how compelling it seems.

## The Seven Guardrails

Every candidate improvement is scored against these before it can become a bead. Failing any one kills the candidate. These are lifted from [[PHILOSOPHY.md]] and restated as a rubric.

**1. Loop placement.** Does this change keep intelligence in the inner loop and orchestration in the outer loop? *Rejected if:* it pushes judgment into bash, encodes ephemeral context into the orchestrator, or moves reasoning out of the model. *Accepted if:* it gives the inner loop better artefacts to reason over, or makes the outer loop's deterministic job more boring.

**2. Simplicity delta.** Net lines added or removed? *Bias strongly toward subtractive.* A candidate that adds code must justify its existence against the alternative of clarifying a template or a bead description. If a prompt tweak works, no bash change is allowed.

**3. Artefact vs decision.** Does this store reusable evidence, or freeze an ephemeral decision? *Rejected if:* it bakes a judgment into code (e.g. hardcoding a task-selection heuristic). *Accepted if:* it produces structured data the inner loop can re-read.

**4. Determinism.** Does failure become more predictable, or does non-determinism sneak in? *Rejected if:* it introduces probabilistic behaviour to the outer loop, or adds a code path whose failure mode is opaque.

**5. Configurable, not required.** New capability must be opt-in via `.ralph/config`. *Rejected if:* it changes default behaviour in a way an existing user did not ask for.

**6. Template vs code.** Instruction changes live in `templates/`. Orchestration changes live in `lib/`. *Rejected if:* a candidate mixes them, or puts natural-language instructions inside a `.sh` file, or puts shell logic inside a template.

**7. Size limits.** File ≤ 200 lines. Function ≤ 50. Case branch ≤ 10. Inline string ≤ 5. *Rejected if:* the candidate violates any of these without explicit approval written into the bead description.

A candidate that survives all seven becomes a bead. A candidate that fails any is noted in the report as *rejected: guardrail N* with a one-line reason. The rejections are as valuable as the acceptances — they record what was considered and why it was not worth doing.

## What the Methodology Harvest Collects

Primary inputs (playlist mode, the common case):

- `.ralph/logs/sessions/<project>-<branch>-<timestamp>.log` — the human-readable session log.
- `.ralph/logs/stream/<session>-<NNN>.jsonl` — per-invocation raw stream-json. Source of truth for turn counts, cost, tool uses, model escalations.
- The playlist file itself — planned order, annotations, gate tags.
- `.ralph/playlist-progress.md` — the snapshot written during the run.
- The playlist completion report — generated by ralph at playlist end.
- Bead state diff — `br` output before vs after the run, to see what changed status, what was created mid-run, what stalled.

Secondary inputs (standard `br ready` mode):

- Same logs and stream files.
- No playlist → no planned-order comparison. The analysis falls back to per-task outcome and circuit-breaker state transitions.

The methodology harvest never reads the code ralph wrote during the run. That is the work harvest's job. Mixing the two is how both get done badly.

## The Classification Pipeline

The collector dumps inputs into the harvest playlist's context. Claude then, guided by the playlist's `>` prompts, produces findings in this order:

**Diagnose.** Where did the run stall, retry, escalate model tier, trip the circuit breaker, or produce shallow gate work? Each of these is a symptom. The diagnosis names the symptom and the evidence (line numbers in the log, turn counts from stream-json, bead IDs).

**Classify.** Each finding is labelled by loop placement: *inner-loop instruction gap* (a prompt or template needs refinement), *outer-loop orchestration gap* (bash needs adjusting), *bead-description shape* (the bead itself was ambiguous), *gate template* (a quality gate template missed a case), or *context injection* (the inner loop lacked state it needed). These are the only five categories. A finding that fits none of them is probably not a methodology finding — it might be a bug for the work harvest.

**Score.** Each classified finding is scored against the seven guardrails. Rejections are recorded with a one-line reason; acceptances proceed.

**File.** Surviving findings become beads, grouped under a single epic, tagged `self-improvement`, titled `HV: <short description>`, typed `chore` (or `bug` for demonstrable orchestration defects). The report is written with the epic ID in the first line.

## The Harvest Playlist

The methodology harvest is itself a ralph task. It runs via `ralph --playlist playlists/harvest-methodology.playlist`. The playlist is hand-authored, checked into the repo, and versioned. It is not generated per-run.

This is deliberate. The methodology harvest uses the same orchestrator it is evaluating. If the outer loop has a bug, the harvest hits it. If the prompt assembly produces bad context, the harvest suffers from it. The tool that improves ralph is ralph. When the methodology harvest itself is awkward to run, that awkwardness becomes a finding.

The playlist's own improvements are found by the next run of the playlist. This is the recursive property of the system.

## Bead / Epic / Report Convention

Formal conventions, lifted out of the narrative for reference:

| Element | Value |
|---------|-------|
| Label | `self-improvement` |
| Title prefix | `HV:` |
| Bead type | `chore` (default) or `bug` (demonstrable defect) |
| Priority | 2 (default), 1 if the finding causes repeated run failures, 3 if cosmetic |
| Epic title | `Harvest YYYY-MM-DD HH:MM — <playlist-or-session-identifier>` |
| Epic always created | Yes, even for single-finding runs |
| Report path | `.ralph/harvests/<YYYY-MM-DD-HHMM>.md` |
| Report opens with | The epic ID, on its own line |
| Report ordering | Findings by guardrail severity (accepted first, rejections after) |

`br list -l self-improvement` becomes the canonical view of pending methodology work. The epic view (`br graph <epic-id>`) shows one run's worth of findings as a unit.

## What the Methodology Harvest Is Not

**It is not a code review.** The work harvest reviews code. The methodology harvest reviews the process that produced it. If a finding reads like "this function has a bug," it belongs in the work harvest, not here.

**It is not model tuning.** The model improves on its schedule. The methodology harvest does not propose changes that amount to "the model should be smarter about X." It proposes changes to the environment the model operates in — the prompts, the context, the gate templates, the orchestration.

**It is not architectural redesign.** The philosophy is fixed. The methodology harvest operates within it, not against it. A finding that implies "rewrite ralph in Go" is out of scope. A finding that says "this gate template is ambiguous" is in scope.

**It is not a grievance log.** Frustrations about run quality that cannot be translated into a concrete, guardrail-surviving bead are noted in the report under *observations* and left there. Not every disappointment is a finding.

## The Discipline

Run the methodology harvest **after every non-trivial ralph run**, but not after trivial ones. A three-bead run rarely produces enough signal to justify the overhead. A twenty-bead overnight run almost always does.

Timebox it. A methodology harvest that takes longer than 15 minutes of ralph wall-clock time is itself a finding — the harvest playlist needs tightening.

Be ruthless with the guardrails. The system improves only when bad candidates are rejected. A harvest that accepts every finding is a harvest that is growing complexity, which is exactly what the philosophy says not to do. Expect to reject more than half of all candidates in a mature harvest. If you are not rejecting, the rubric is not being applied.

Act on the epic within a week. Self-improvement beads that sit for a month stop being improvements — the context that produced them has moved on. If you will not act on them, close them as `wontfix` with a reason. Do not accumulate.

Revisit the rubric annually. The seven guardrails are derived from the current philosophy. If the philosophy shifts, the rubric follows. Not before.
